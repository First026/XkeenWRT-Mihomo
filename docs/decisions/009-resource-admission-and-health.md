# 009. Ресурсы runtime и стоимость проверки core

Дата: 12 ноября 2026. Статус: согласованный дизайн для реализации и испытаний в VM. Приведённые пределы ещё не подтверждают пригодность для роутер.

## Основание

Read-only inventory целевого роутера показывает около 485 MiB RAM и 167 MiB свободного overlay. Ограничение размера YAML не ограничивает память самого Mihomo. При аудите live core имел cgroup для идентификации и остановки, но не hard memory/PID limits; история ограничивалась числом записей, а не общим размером. Независимая health-проверка могла дважды читать и хешировать около 60 MiB executable каждые пять секунд.

Это открытые условия готовности пунктов 1–6, связанные с сохранностью подключения. VM с увеличенной памятью для упаковки initramfs не является доказательством работы на устройстве с меньшей RAM.

## Начальные пределы стенда

| Область | Решение |
| --- | --- |
| Только cgroup core | `memory.max=201326592`, `memory.swap.max=0`, `pids.max=64`, `memory.oom.group=1` |
| Начальный допуск RAM | `MemAvailable` не менее 256 MiB перед подготовкой и остановкой прежнего core |
| Временный home | Свободное место `/tmp` не менее 32 MiB плюс два новых bundle для staging и возврата прежнего состояния |
| Постоянное хранилище | Не менее 32 MiB свободного места плюс фактические дополнительные journal/history/staging bytes с учётом сериализации |
| История | Не более 64 MiB суммарно; отказ до новой записи, без удаления pinned current/previous/baseline |

Пределы записываются и читаются обратно до выдачи launch grant. `core-run` повторно проверяет значения и своё членство до `exec`. Неподдерживаемые контроллеры или неоднозначная принадлежность приводят к отказу до старта. Глобальные контроллеры и чужие cgroups не перенастраиваются молча. Stop и cleanup не зависят от свободной памяти или исправности нового admission gate.

Фиксированный порог RAM намеренно консервативен: он может отклонить обновление работающего core, хотя часть его памяти позднее освободится. Оптимизация возможна после измерений и доказанной идентификации учитываемой памяти. Порог не обещает резервирования RAM от сторонних процессов; hard cgroup cap ограничивает собственный core.

Страницы tmpfs, созданные core, учитываются его memory cgroup. Это не глобальная квота `/tmp` и не ограничение записей других процессов. Managed policy отключает `store-selected`, `store-fake-ip`, загрузку geodata и автоматическую запись providers. Реальные файлы, создаваемые закреплённым Mihomo при таком профиле, должны быть наблюдены в VM. Нельзя разрешать неизвестные cache-файлы в проверке home или обещать их очистку без проверки.

## Проверка executable без повторного полного SHA

Health module может держать ровно одну запись в памяти процесса с открытым FD проверенного executable. Запись создаётся только после совпадения с закреплённым SHA и одинаковых metadata до и после чтения. На каждом наблюдении заново проверяются `/proc/PID/exe`, точный путь, владелец, mode, link count, размер и tuple `(dev, ino, mtime_ns, ctime_ns)` против удержанного FD. Изменение требует повторной проверки или отказа. Cache не сохраняется на диск и не доверяет одному имени файла или номеру inode.

Cache не заменяет PID/starttime, launch nonce, grant, home/config/assets, cgroup или владение socket. Эти свидетельства повторно проверяются до и после запроса к controller. Неоднозначность означает `Unavailable`, а не автоматически доказанный отказ core.

## Проверки перед приёмкой

- В VM подтвердить readback caps, отказ при недостатке RAM/flash и возможность Stop при отказавшем admission.
- Проверить исчерпание памяти только внутри собственного core cgroup, работоспособность независимого helper и неизменность управления/чужих процессов.
- Проверить историю на границе байтового лимита и сохранность pinned snapshots при отказе новой записи.
- Измерить steady-state память, временные файлы и время health tick с cache hit и miss; отдельно проверить executable replacement и metadata drift.
- Повторить финальный сценарий на ARM64 VM. Не переносить числа x86 TCG на физический роутер без отдельного согласованного этапа.

Реальные результаты и точные artifacts записываются в лабораторном отчёте. Этот документ не объявляет проверки пройденными и не разрешает испытания на рабочих роутерах.

## Уточнение r23: повторные наблюдения

Чистая структурная проверка journal может иметь одну process-local memo entry, ключом которой служит всё сериализованное содержимое с прежним пределом 1 MiB. Результат `Decision`, время, boot-id, startup/restart, чтение файла, права, owner, fence и lifecycle не кешируются. Ошибка чтения не разрешает использовать прежний journal. Изменение любого поля заново запускает полную структурную проверку.

В одном read-only health cycle под mutation lock один current/previous view используется для core health и проверки topology. Наблюдение не передаётся в mutation/restore: эти границы сохраняют свежие проверки. Два чтения live home и identity вокруг controller round trip остаются.

Общий HTTP snapshot предназначен только для отображения `/api/control` и `/api/inputs`. Epoch invalidation до и после owner action не позволяет опубликовать старую in-flight запись. Технический fresh header служит проверке завершения действия; браузерный `Cache-Control` не обозначает свежесть runtime-доказательств. Confirm использует независимый свежий сетевой endpoint и не принимает display snapshot как разрешение.
