# 025. Повтор отключения после разовой ошибки recovery

18 ноября 2026, выпуск 0.1.26.4. Уточняет решения 007 и 021. Владелец заказал разбор зависания Stop и его исправление («Да, разобрать», затем «Да, делай»).

## Контекст

Recovery выполняет активное событие по шагам: `Intent` → `NftDone` → `RoutingDone` → `BaselineDone` → `Verified`. Ошибка шага переводит запись в `Error` с кодом. Код `RECOVERY` означает разовую ошибку команды или ввода-вывода в собственном шаге recovery (`recovery()` в `recovery/src/active_driver.rs`). Для `CoreFailed` и `ReconcileRequested` такая ошибка повторялась до двух раз с упавшего шага. Для `DisableRequested` — отключения, которое запрашивают Stop и «Выключить перехват» — повтора не было.

На стенде 0.1.26.3 (прогон 3, [приёмка](../testing/2026-11-18-0.1.26.3-lab-acceptance.md)) Stop сразу после «Перезапустить» упал в `restore_baseline` уже после снятия nft и маршрутов. Запись осталась в `Error` навсегда. Статус показывал `degraded`, Stop с тем же ключом отвечал `BUSY`, Start — `409 CONFLICT`. Помогало только «Выключить перехват» с новым ключом. Текст ошибки recovery отбрасывал, поэтому причина неизвестна; цикл из 14 повторов на диагностической сборке её не воспроизвёл (журнал).

## Решение

**Повтор.** Код `RECOVERY` повторяется для всех трёх видов событий, включая `DisableRequested`, по тому же правилу: не больше двух повторов, с упавшего шага, на том же boot. Уже выполненные шаги (снятие nft и маршрутов) не повторяются. Повторяет сам recovery-супервизор: он обрабатывает сохранённое событие на каждом проходе цикла (раз в 0,1 с, при ожидании runtime — раз в 1 с). Пользователю ничего нажимать не нужно. Коды `INVALID`, `DRIFT`, `UNAVAILABLE`, `HEALTH` и `STORAGE` по-прежнему не повторяются: это не разовые сбои.

**Причина в журнале.** Каждый шаг, который меняет сеть или ядро (снятие и восстановление nft и маршрутов, возврат ядра, итоговая проверка, запись журнала), при ошибке пишет в stderr супервизора одну строку: `recovery step failed: step=<шаг> kind=<вид> os_error=<errno>: <текст>`. Procd передаёт её в syslog (`logread`). Ошибки ввода-вывода std не содержат путей и секретов. Периодические наблюдения раз в 5 с строку не пишут, чтобы при постоянном сбое не засорять журнал; у шагов не больше трёх попыток на событие.

**Формат не меняется.** Поле `retry_failures` уже было в записи, и проверка записи принимает его для любого вида события. Записи 0.1.26.4 читаются rescue 0.1.26.3.

## Чего это не решает

- Неизвестную исходную ошибку. Строка в журнале покажет её при следующем случае.
- Ошибку, которая держится дольше двух повторов. Тогда, как и раньше, выход — «Выключить перехват», затем Stop.

## Проверка

- Тесты `recovery/tests/active_contract.rs`. Первый — разовая ошибка `restore_baseline` у отключения доходит до `Disabled`, продолжая с упавшего шага. Второй — постоянная ошибка ограничена двумя повторами, `HEALTH` не повторяется. На коде 0.1.26.3 оба падали.
- Тесты строки журнала в `recovery/src/active_driver.rs`.
- Стенд, сценарий С8: на работающем шлюзе каталог ядра намеренно делается небезопасным, и Stop падает на возврате ядра. После первой ошибки права возвращаются, и отключение завершается само, а в `logread` есть строка с шагом `restore_baseline`.
