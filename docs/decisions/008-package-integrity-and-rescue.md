# 008. Целостность APK и восстановление после удаления

Дата: 12 ноября 2026. Статус: принято для реализации; окончательная приёмка открыта. Основание — реальные эксперименты из отчёта APK, а не предположение об атомарности пакетного менеджера.

## Наблюдаемые ограничения

В OpenWrt 25.12.6 APK 3.0.5 продолжил удаление пакета и вернул успех после exit 1 из pre-deinstall. Ошибка hook не является veto. При ENOSPC обновление вернуло ошибку, сохранило прежнее ядро и пользовательские данные, но база пакетов показала UI r2 и core r1. Точное dependency constraint не обеспечило транзакционность обновления пары.

Стандартные hooks OpenWrt автоматически запускают/включают init scripts и останавливают их до custom pre-remove. Поэтому inert пакет хранит init payload вне `/etc/init.d`; собственный ограниченный hook создаёт только фиксированные symlinks. Install не запускает core, не включает сетевой режим и не создаёт маркеры разрешения deployment.

## Проверка перед выполнением

Runtime проверяет точные версии установленных UI/core и compile-time package version. Эта проверка обнаруживает известное расхождение r1/r2, но сама по себе не доказывает целостность файлов после неполной распаковки.

Дополнительно пакет содержит ограниченный root-owned manifest с version, уникальным build-id и SHA-256 компонентов по фиксированным путям. Build-id вычисляется до компиляции backend из identity замороженных исходников, версии пакета, закреплённого core, точных validator/recovery/init inputs. Backend включает этот build-id при сборке; упаковщик самостоятельно перепроверяет digest и фактические файлы. Manifest может содержать hash backend без циклического self-hash, поскольку backend включает build-id, а не hash готового manifest.

Перед validate/apply/start/core-run нужны совпадающие build-id/version и hashes фактических компонентов, безопасные ownership/mode и отсутствие symlink/неожиданных путей. Старый выполняющийся backend с новым manifest, новый файл со старым manifest и частичный комплект должны отказать до запуска. Stop и собственная аварийная очистка остаются доступны. Версии и build-id релизов не переиспользуются для других inputs.

Проверка не делает APK атомарным. Она ограничивает последствия неполного обновления: неподтверждённый комплект не получает право выполнять профиль или менять сеть. Повторная установка исправного комплекта и сохранение пользовательских данных проверяются отдельно.

## Persistent rescue

До первого ручного запуска core или сетевого применения provision создаёт проверенную статическую копию rescue executable и отдельный procd service вне удаляемого APK payload, в private `/etc/xkeenwrt/rescue`. Install APK не выполняет provision. При явной активации создаются только boot-links cleanup supervisor: `S09xkeenwrt-rescue` и `K91xkeenwrt-rescue`; runtime/core/network не включаются при загрузке. Приёмка должна подтвердить порядок загрузки и сохранность rescue после удаления UI и core. Совместимость rescue с новой схемой журнала проверяется до каждой новой активации; существующую действующую копию нельзя слепо перезаписать во время upgrade.

Persistent init `/etc/init.d/xkeenwrt-rescue` публикуется из шаблона, включённого в бинарник recovery. Его ожидаемые bytes/hash не берутся из произвольного внешнего manifest. Файлы rescue и его init не входят в изменяемый APK payload. Новая копия может заменить прежнюю только после доказанной очистки, остановки собственных сервисов/cgroups и проверки отсутствия собственных сетевых объектов.

Pre-remove записывает durable запрос удаления и ограниченно ожидает результат. Exit code hook — лишь диагностика. Rescue отзывает grant, запрещает новые мутации, останавливает собственные runtime/core через фиксированный ubus API даже при исчезнувших init scripts, подтверждает завершение cgroups и удаляет только точные собственные nft/routes/rules. При удалении пакета не следует восстанавливать запуск уже удалённого Mihomo.

`cleanup_complete` появляется только после проверки отсутствия собственных объектов и процессов. При неполной очистке rescue и durable запрос сохраняются для повторной попытки. Обычный post-remove не удаляет rescue. Завершающее удаление rescue — отдельная операция после доказанной очистки.

Если pre-remove не может получить подтверждение rescue, package hook ограниченно останавливает UI и runtime через их точные init-ссылки и проверяет состояние procd. При неизвестном статусе он сохраняет ссылки. Core/recovery без rescue останавливаются только при наличии root-private `network-never-enabled` и отсутствии network journal; неизвестное сетевое состояние остаётся запущенным и не считается очищенным. Ошибка hook не отменяет APK удаление, поэтому rescue остаётся независимым механизмом для обычного поддерживаемого пути.

После подтверждённого Remove владелец может отдельно запустить persistent helper с точным request-id: `/etc/xkeenwrt/rescue/xkeenwrt-recovery --finalize-remove <request-id>`. Команда останавливает rescue/package recovery через fixed ubus-команды в owned cgroup, берёт общие lifecycle locks, повторно подтверждает `cleanup_complete`, выключенную сеть и точное владение текущими/архивными rescue bundles, затем удаляет только init/boot links и проверенные rescue assets. Эта операция необратимо завершает доступ к Resume через удалённый helper; обычный APK Remove её не вызывает.

Отсутствие сетевого журнала не доказывает отсутствие ранее созданной сети. Быстрый путь допускается только при настоящем root-private `network-never-enabled`, отсутствии собственной таблицы и подтверждённой остановке собственных сервисов. Этот marker создаётся лишь при первоначальном bootstrap; перед первой сетевой мутацией он удаляется с fsync и не создаётся заново при утрате журнала.

Системные инструменты rescue (`nft`, `ip-full`, `ubus`) должны переживать удаление пакетов проекта. Сетевые зависимости ставятся отдельно; нельзя полагаться на автоматическое сохранение зависимостей UI. В рамках текущей работы все сценарии удаления, ENOSPC и остановки процессов выполняются только в одноразовой VM.

## Обновление действующего экземпляра

`--prepare-upgrade` создаёт отдельный durable запрос с purpose `upgrade`. Его нельзя подменять запросом удаления. Rescue ограниченно останавливает собственные runtime/core, снимает собственную сеть и фиксирует receipt очистки; hook не возобновляет профиль и не очищает fence. Если APK продолжит обновление несмотря на ошибку hook, независимый rescue сохраняет запрос и продолжает восстановление.

При последующем явном запуске новый runtime проверяет целостность всего комплекта и receipt очистки; только затем может завершить точный upgrade request через generation/CAS. При неполном комплекте fence остаётся. Сетевой режим требует нового plan/apply, ручной core запускается только явным действием. Removal fence не очищается этим путём. Никакая успешная запись APK database сама по себе не разрешает запуск.

## Явное возобновление после повторной установки

Дополнение от 13 ноября 2026. Реализовано и проверено в x86 VM на точном комплекте r3: Resume после инертной повторной установки того же комплекта оставляет core остановленным, отдельный Start запускает его. Неверный и повторный request-id отклоняются. Артефакты и границы результата — в checkpoint. Замена версии helper, reboot, сетевой режим, ARM64 и физический роутер этим не подтверждены.

После Remove пользователь выбирает отдельное действие **«Возобновить после переустановки»**. Оно возвращает возможность проверять и применять профили, оставляя Mihomo остановленным. Обычные Start, install hooks, открытие страницы и чтение состояния не снимают Remove fence. Это позволяет сохранить смысл удаления и работать с сохранёнными данными даже без ранее принятого ручного профиля. Запуск core и новое сетевое plan/apply остаются отдельными действиями.

Первый поддерживаемый случай — повторная установка того же проверенного комплекта: package build-id и SHA-256 recovery должны совпадать с persistent rescue. При другой версии helper возобновление отказывает с отдельным результатом о необходимости согласованной замены rescue. Нельзя очищать receipt, переименовывать Remove в Upgrade или ослаблять `UpgradeSpec::valid()` ради этого случая. Переустановка с заменой helper остаётся отдельным незакрытым условием.

Интерфейс операции принимает только точный request-id завершённого Remove, показанный аутентифицированному владельцу в состоянии установки. HTTP-прослойка не принимает пути, команды или флаг обхода проверки. Неверный либо устаревший request-id, незавершённая очистка и действующий upgrade intent запрещают операцию без изменения receipt. Повтор после уже завершённого возобновления не запускает core и не снимает последующий запрос удаления.

Порядок:

1. Под общим mutation lock проверить root-private owner/Remove/cleanup_complete, точную пару APK и manifest, закрепить recovery ELF, подтвердить совпадение persistent rescue и отсутствие незавершённой замены helper.
2. Проверить остановку core, отозванный launch grant, пустые собственные command cgroups и отсутствие собственной сети. Допускаются только текущие проверенные runtime и UI, необходимые для запроса. Проверки собственности и quiescence должны разделять существующий production-механизм с Upgrade; нельзя заменять их одной проверкой имени процесса.
3. Освободить mutation lock перед ожиданием helper. Получить отдельный READY для возобновления, привязанный к Remove request-id, owner, boot, PID/starttime, supervisor nonce и проверенному executable. Marker публикует сам persistent helper после чтения соответствующего завершённого Remove. Отсутствие marker не заменяется одним наличием PID. Upgrade READY сохраняет свой прежний контракт.
4. Снова взять lock, перечитать точный request, повторно проверить пакет и закреплённый ELF, helper/READY, отсутствие upgrade intent и quiescence. Смена любого участника отменяет операцию.
5. Завершить оставшуюся ручную транзакцию без запуска core, подготовить его пустой cgroup и последней durable мутацией снять только соответствующий Remove receipt. Вернуть состояние «возобновлено, Mihomo остановлен». Нельзя вызывать manual recover, который восстанавливает `restore_running`, пока этот пункт не завершён.

Отдельный журнал замены helper этому случаю не нужен: до последнего удаления receipt все операции остаются запрещены; после него core по-прежнему остановлен, а новая активация требует команды владельца. Авария до снятия receipt допускает безопасный повтор проверок; ошибка после unlink/fsync требует повторного чтения состояния, а не сообщения об успехе. Чужие файлы, профили и история не меняются; сетевой marker никогда не создаётся заново для обхода утраченного журнала.

Проверки реализации: положительный переход Remove → возобновлено/остановлено; запрет Upgrade, Requested, неверного owner/request-id, повреждённого/несовпадающего пакета, живого core и stale/missing READY; отсутствие автозапуска при повторе/ошибке; сохранение данных; затем отдельный обычный HTTP Start. Сквозной VM-сценарий использует новый точный комплект с этим протоколом, а не объявляет ранее испытанные r2 APK проверкой нового кода. Обновление UI проверяется на отсутствие автоматического POST при загрузке и понятное разделение возобновления и запуска.

Для доступности этих действий HTTP `/api/platform` получает признак поддержки ручного управления из ограниченного read-only ответа native runtime с разрешённым deployment. Сам `Platform::inspect()` остаётся простым определением платформы: проверки deployment/package уже используют его, поэтому обратный вызов создал бы рекурсию. Preview, неподдерживаемая платформа и недоступный runtime не получают `core_control`. Этот признак не снимает fence и не подтверждает готовность профиля; Start и Resume проверяют свои условия заново. Несовместимость пакетов сама по себе не должна скрывать возможность аварийного Stop. Сетевые и provider capabilities этим изменением не включаются.

## Оставшиеся доказательства

Для ручного режима на x86 уже подтверждены отдельные случаи продолжения rescue после исчезновения payload и автоматической обработки Requested после реальной перезагрузки. Это не приёмка всей матрицы ниже: сетевой режим, другие точки отказа, окончательная сборка ARM64 и целевое устройство остаются открытыми.

Нужны проверки точных production ELF и manifest, отказ при каждой комбинации частичного обновления, безопасный stop при несовместимой паре, удаление во время pending/confirmed network generation, потеря pre-remove hook, продолжение rescue после исчезновения APK payload, reboot с durable запросом и проверка неизменности чужих объектов. Промежуточный lifecycle PASS их не заменяет.

## r22: отдельная чистая установка после завершённого Remove

Для разных Build ID strict Resume остаётся прежним. После штатного `--finalize-remove` старого persistent helper отдельный проверенный r22 recovery ELF поддерживает `--archive-finalized-remove <request-id>`. Команда допускается только после удаления APK payload/init и всех procd definitions, с lifecycle locks, exact completed Remove, отозванным grant, пустыми собственными cgroups и проверенным отсутствием собственных сетевых объектов. Она переносит весь прежний `/etc/xkeenwrt` в фиксированный sibling `xkeenwrt-retired-<request-id>` через `RENAME_NOREPLACE` с fsync родителя. Старые YAML, owner, journal и fence сохраняются вместе; новая установка создаёт новый state и не импортирует их. Собственные ephemeral каталоги переносятся только внутри своих parents до последнего persistent rename. Ошибка/прерывание сохраняет старый fence; старый request не применяется к новой установке. Порядок действий владельца: [чистая переустановка](../clean-reinstall.md). Native-приёмка этой команды фиксируется отдельно от host receipt/archive regressions.
