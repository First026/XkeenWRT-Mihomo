# 024. Запуск шлюза через Tailscale

**Статус: действует. Владелец вернул 18.11.2026** (выпуск 0.1.26.3).

17 ноября 2026. Уточняет решения 002, 007 и 021. Основание — ТЗ r26.1, утверждённое владельцем. Цель — OpenWrt 25.12.6, `aarch64_cortex-a53`.

**История.** Решение реализовал выпуск 0.1.26.1. 18.11 владелец его отменил: решил, что запуск через Tailscale не заказывал. Выпуск 0.1.26.2 вышел без этой функции. В тот же день владелец решение вернул: ▶ «Запустить» должен работать через Tailscale, как в оригинальном XKeen-UI на Keenetic. В 0.1.26.3 код 0.1.26.1 перенесён поверх 0.1.26.2 без изменений; исправление «Применить» на работающем шлюзе (`operation_profile`) было в обоих выпусках и сохранено.

## Контекст

По решению 021 через Tailscale-вход панели были доступны статус, Stop и выключение перехвата, а включение шлюза, Restart и Apply при активном шлюзе требовали клиента основной IPv4 LAN. 17.11 владелец был вне дома и не мог нажать ▶: кнопка выключена, API отвечает `NETWORK_MANAGEMENT`.

Разбор показал, что прежнее подтверждение доказывало меньше, чем казалось. Интерфейс отправляет Confirm сразу после свежего запроса статуса от того же клиента, а `health()` проверяет только, что ядро живо. Трафик управляющего клиента к роутеру перехватом не затрагивается (`ip daddr <управление> return`, локальные сети LAN тоже исключены). Значит, подтверждение из LAN доказывало сохранность пути управления и здоровье ядра, но не работу DNS и выхода для домашних устройств.

Путь через Tailscale от перехвата не зависит. Захват цепляет только `prerouting` с `iifname br-lan` и источником из LAN. Трафик `tailscaled` исходит от самого роутера (`output`), вход `tailscale0` не захватывается, правило маршрутизации проекта срабатывает только на метку захвата.

## Решение

**Канал задаёт listener, а не адрес.** HTTP-слой передаёт в runtime `ManagementPeer::{Lan, Tailscale{peer, router}}`. Tailscale-вариант выдаёт только узкий listener `tailscale0` из решения 021, привязанный к устройству и адресу. Адрес из 100.64.0.0/10, пришедший на LAN-listener, остаётся LAN-пиром и, как прежде, отвергается правилом LAN.

**Допуск.** Для Tailscale-пира проверка `management` проходит, только если текущая граница `tailscale0` имеет тот же адрес роутера, что и принявший listener, роутер — usable host единственной LAN-подсети, а пир лежит в 100.64.0.0/10 вне LAN. Правило `valid_whole_lan_management(scope, router, peer, channel)` общее для плана, манифеста и доказательства сети.

**Манифест.** `Manifest`, `OwnedManifest` и `evidence::Scope` получают необязательное поле `management_channel` (`"tailscale"`). У запуска из LAN поля нет (`skip_serializing_if`), байты и хеши такие же, как в r26, и rescue r26 их читает. Tailscale-канал допустим только для «всей LAN» с `direct_on_failure`. Пилотный клиент, block-политика и HTTP/SOCKS остаются действиями из LAN. Правила nft Tailscale-плана совпадают с LAN-планом, кроме адреса в `ip daddr … return`.

**Подтверждение.** Для Tailscale-поколения Confirm после проверки здоровья ядра вызывает `remote_check`, затем заново проверяет срок и fence:

- DNS — запрос `A www.gstatic.com` на `lan_address:1053` с loopback (его пропускает `inputguard`), ответ NOERROR с записью A, две попытки по 3 с;
- выход — до 8 узлов из `/providers/proxies`, по 4 параллельно, таймаут 4 с: узлы `proxies:` через `/proxies/{узел}/delay`, узлы подписок через `/providers/proxies/{провайдер}/{узел}/healthcheck`. Встроенные исходящие и группы не считаются. Нет ни одного узла — проба пропущена. Недоступный контроллер — провал;
- справочно — число LAN-адресов с соединениями `TProxy` и `download > 0` в `/connections`.

Провал даёт `NETWORK_REMOTE_DNS` или `NETWORK_REMOTE_EGRESS` с отчётом `remote_check`; журнал остаётся Pending, и rescue снимает его не позже срока. Отчёт последнего подтверждения хранится только в памяти runtime и показывается в `/api/network/status` вместе с `management_channel`.

**Интерфейс.** При отказе проверки после ▶ или «Перезапустить» панель сразу вызывает «Выключить перехват»: предыдущего поколения нет, LAN возвращается в Direct, не ожидая 120 с. После «Применить» на работающем шлюзе этого не делается: по решению 021 выключение во время замены уводит в Direct, а откат по сроку возвращает прежнее рабочее поколение.

**Restart через Tailscale** разрешён, только если выбран один шлюз; при выбранном HTTP/SOCKS отказ происходит до остановки, как и прежде.

## Почему не иначе

- Определять канал по адресу 100.64/10 нельзя: такой адрес может прийти через subnet route или CGNAT провайдера.
- Синтетический клиент (veth + netns в `br-lan`) прошёл бы весь путь, но на рабочем роутере нет модуля `veth` и сетевых namespace, а ставить kmod на рабочий роутер запрещает решение 002.
- `/group/GLOBAL/delay` в Mihomo 1.19.34 не видит узлы proxy-providers (проверено 17.11), поэтому кандидаты берутся из `/providers/proxies`.
- Требовать живой трафик домашних устройств нельзя: если дома всё спит, удалённый запуск всегда откатывался бы. Он только показывается.

## Совместимость

- 0.1.26.2 → 0.1.26.3: журнал и манифесты 0.1.26.2 (формат r26) читаются без изменений.
- 0.1.26.3 → 0.1.26.2 после Tailscale-запуска: rescue 0.1.26.2 не прочитает поле канала (`deny_unknown_fields`). Запретить откат хуком нельзя, при установке 0.1.26.2 выполняются его скрипты. Откат — чистой переустановкой или после запуска из LAN ([инструкция](../clean-reinstall.md#откат-01263--01262)).
- Версия пакетов — `0.1.26.3-r0`, тег `v0.1.26.3`: apk-tools 3 не принимает `0.1-r26.3`.

## Проверка

Unit и контрактные тесты: правило Tailscale в manifest/evidence/plan/compatibility, неизменность LAN-сериализации, пробы на форматах Mihomo 1.19.34, Confirm с отказом проб, Restart и HTTP/SOCKS, отказ отката в журнале, интерфейс. Лабораторная приёмка — в [отчёте 0.1.26.3](../testing/2026-11-18-0.1.26.3-lab-acceptance.md). Настоящий Tailscale с DERP и топология рабочего роутера в VM не воспроизводятся; на рабочем роутере — только по отдельному «да» владельца.
