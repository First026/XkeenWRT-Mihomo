# 006. Проверка отдельного supervisor валидатора в VM

Статус: лабораторное архитектурное решение; реализация и испытания фиксируются отдельно в журнале. Это не разрешение запуска на роутере и не готовый production validator. Основания — исследование изоляции, стенд OpenWrt и [сохранность роутеров](002-router-preservation.md).

Для лабораторной проверки выбран отдельный небольшой native supervisor, запускаемый как самостоятельный однопоточный процесс. Он проверяет порядок установки ограничений непосредственно через Linux API. Обычный `ujail -S` не фильтрует статический Mihomo; OCI-вариант требует дополнительной проверки и независимого контроля cgroup. Это оставляет ujail возможной альтернативой, но не делает его готовой границей безопасности. Системный `fork` с произвольной Rust-логикой внутри многопоточного Tokio HTTP-процесса не используем.

## Лабораторный interface

Отдельный crate в `tests/lab/validator/` поставляет supervisor и тестовый процесс. Interface — фиксированный набор сценариев, а не произвольные команды, пути, URL или пользовательские YAML. Запуск разрешён только внутри специально маркированной disposable VM. На хосте разрешены компиляция и проверка отказа до любых привилегированных действий. В production backend/frontend этот код пока не подключается.

Supervisor и настоящий закреплённый Mihomo проходят один путь подготовки дочернего процесса: закрытый gate до подтверждения cgroup, private mount/net/PID/IPC/UTS namespaces, ограниченный tmpfs, только явно подготовленные файлы и read-only executable, смена root и cwd, закрытие FD, чистое окружение, необратимый сброс UID/GID/groups/capabilities, no-new-privs и seccomp до exec. PID namespace исключает обращения сигналами к посторонним процессам с тем же UID; IPC namespace отделяет System V IPC от остальных процессов гостевой системы. Доверенный setup/wait процесс тоже входит в cgroup задания. Системные файлы, proc/sys/dev и сервисные Unix sockets внутри sandbox отсутствуют. Отдельный supervisor остаётся вне cgroup задания. Syscall-фильтр обязан проверять архитектуру, запрещать сокеты, ptrace/process-vm и обход через io_uring/смену namespaces; наличие фильтра проверяется до запуска.

Лимиты memory/pids/swap устанавливаются и читаются обратно до освобождения child gate; запись PID и принадлежность к cgroup также проверяются. Время измеряется монотонно, вывод ограничивается при чтении и не публикуется как сырой журнал ядра. Завершение убивает всё задание через cgroup, собирает потомков и подтверждает отсутствие процессов и временных ресурсов. Ошибка setup или cleanup означает отказ. Произвольный `mihomo -t` вне этого пути не является fallback.

Seam испытаний — результат фиксированного сценария и наблюдаемое поведение тестового executable через тот же запуск. Последовательно проверяются: недоступность внешнего синтетического sentinel/унаследованных FD и окружения; невозможность создать IPv4/IPv6/Unix sockets и вернуть привилегии; квота tmpfs; ограничение числа процессов и очистка потомков; timeout/переполнение вывода; локальный OOM внутри ограниченного задания; отказ setup до exec. Только после проверок обычного процесса допускается закреплённый Mihomo с синтетическими valid/invalid/missing-asset/path fixtures. Наличие cgroup-файлов само по себе не считается доказательством.

## Архитектуры стенда

Один путь подготовки задания используется для x86-64 и AArch64. Сборка разрешена только для 64-битного little-endian Linux этих двух архитектур. Seccomp проверяет соответствующий `AUDIT_ARCH`; на x86 дополнительно отклоняется x32, на ARM — несовпадающие совместимые ABI. Номера системных вызовов берутся из целевого libc; отсутствующий там AArch64 `kexec_file_load` явно запрещён по номеру 294 из Linux UAPI. Ослабленного запасного фильтра нет.

Для ARM используется полная VM `virt` с Cortex-A53 и закреплёнными официальными ядром/rootfs OpenWrt 25.12.6 для `armsr/armv8`. Это позволяет проверить механизмы ядра AArch64, которые не подтверждаются эмуляцией одного userspace-процесса. Отдельный отчёт фиксирует результаты; конфигурация ядра и оборудование роутер `mediatek/filogic` этим не проверяются.

## Ограничения результата

Параметры VM и задания — лабораторные, а не обещание RAM budget роутера. Read-only bind доверенного executable из guest rootfs не открывает остальной rootfs; его происхождение/hash проверяются при сборке лабораторного образа. Секретов и файлов реальных устройств в fixtures нет. Исходные образы стенда закреплены; runtime VM остаётся без NIC, дисков, host mounts и дополнительных контейнерных привилегий.

Эта проверка не закрывает физический роутер и его конфигурацию ядра, полную схему и получение assets, устойчивость production supervisor к собственной аварии, runtime IPC, HTTP admission, APK/procd lifecycle, activation/journal/recovery или сеть. До отдельного внедрения и приёмки этих частей `PreparedPreview` остаётся `core_validation: not_run`, `activatable: false`. Все аварийные сценарии выполняются только в VM.
