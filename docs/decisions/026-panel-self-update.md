# 026. Обновление XkeenWRT из панели

18 ноября 2026, выпуск 0.1.26.4. Владелец заказал: «при выборе версии из панели обновлять её», без переустановки по SSH, как в XKeen UI. Дополняет решения 002 и 008.

## Контекст

Кнопка с версией в верхней панели перешла из XKeen UI и открывала окно выбора версии в режиме `self`. В порте у неё не было серверной части, и окно отвечало «Не удалось получить список релизов». В XKeen UI обновление само заменяет исполняемый файл. Для XkeenWRT так нельзя: по [решению 008](008-package-integrity-and-rescue.md) пакеты сверяются с manifest и Build ID, а обновление пары идёт через хуки APK и rescue (`--prepare-upgrade`). Проверенный путь обновления один — установщик `install.sh` из быстрого старта.

## Решение

**Тот же установщик.** Панель запускает `install.sh` выбранного релиза — тот же файл, что команда быстрого старта для этой версии. Он проверяет OpenWrt, SHA-256 обоих APK и версию, с которой обновляет, и ставит пару через `apk`. Второго пути установки нет.

**Список версий.** `GET /api/self/catalog` читает `api.github.com/repos/First026/XkeenWRT-Mihomo/releases`. В окне — только опубликованные релизы новее установленного; черновики, пре-релизы и чужие формы тегов не показываются. Откатиться на старую версию из панели нельзя: старый установщик не обновляет новую пару, а форматы данных проверяются только вперёд. Если есть версия новее, кнопка версии подсвечивается, как в XKeen UI.

**Запуск.** `POST /api/self/update` принимает только номер версии. Репозиторий зашит в сборку; путь, URL, команду или флаг передать нельзя. Панель:
1. отказывает, если шлюз работает (`GATEWAY_RUNNING`, как у обновления Mihomo), если версия не новее (`NOT_NEWER`), если её нет в списке релизов (`UNKNOWN_RELEASE`) и если обновление уже идёт (`UPDATE_RUNNING`);
2. скачивает `raw.githubusercontent.com/First026/XkeenWRT-Mihomo/v<версия>/install.sh` (только HTTPS, без перенаправлений, не больше 64 КиБ) и проверяет, что это установщик этой версии этого репозитория: строки `version=<версия>-r…`, `tag=v<версия>`, `repo=First026/XkeenWRT-Mihomo`;
3. кладёт его в новый каталог `/tmp/xkeenwrt-self-update` (root, `0700`) и запускает временный сервис procd `xkeenwrt-self-update` через `ubus call service set`. Программа сервиса постоянная: `umask 077`, `sh ./install.sh`, вывод — в `log`, код выхода — в `exit`.

Отдельный сервис нужен, потому что обновление APK останавливает и перезапускает сервис панели вместе с его процессами. Временный сервис не входит в список собственных сервисов, которые останавливают хуки и rescue, и доживает до конца установки.

**Ход и результат.** `GET /api/self/update/status` возвращает состояние (`running`, `done`, `failed`, `interrupted`), код выхода, хвост журнала установщика и версию ответившей панели. Без кода выхода запуск моложе 60 с считается запускающимся, а не прерванным: procd стартует экземпляр асинхронно. Если procd не ответил, запуск тоже считается идущим. Временный сервис удаляется только после появления кода выхода, а новый запуск начинается, только когда procd подтвердил, что установщик не работает. Иначе сбой `ubus` во время долгой установки мог бы оборвать её посреди `apk`. Готовый результат читает уже новая панель. Файлы результата пишет панель той версии, которая начала обновление. Поэтому в закрытом каталоге принимаются и файлы, созданные с umask procd 022; отвергаются только доступные на запись группе или остальным. Окно обновления опрашивает статус. Молчание панели — ожидаемый перезапуск, а не ошибка. Обновление закончено, когда ответила панель новой версии.

**Вход.** На управляющих входах — LAN и Tailscale — панель работает без пароля (доверенный доступ), и окно просто продолжает опрос после перезапуска. В режиме с паролем сессии хранятся в памяти панели, и после перезапуска старый вход не действует. Проверку входа ради этого не ослабляем: окно запоминает целевую версию в `sessionStorage` вкладки и перезагружает страницу, а после входа панель читает результат и показывает его.

**Доверие.** Как у быстрого старта: GitHub по HTTPS с системными корневыми сертификатами, хеши APK — в `install.sh` релиза. Подписи пакетов нет. Тот, кто управляет репозиторием, может выпустить любое обновление — и для команды быстрого старта тоже.

**Шлюз.** Обновление идёт только при остановленном шлюзе. После обновления шлюз не запускается сам ([решение 008](008-package-integrity-and-rescue.md)): нужно нажать «Запустить».

## Контракт для следующих выпусков

Панель 0.1.26.4 будет обновлять и на версии, о которых ещё не знает. Каждый следующий выпуск должен сохранить:
- имя тега `v<версия>` и `install.sh` в корне дерева тега со строками `version=`, `tag=`, `repo=`;
- запуск `install.sh` без аргументов: он сам скачивает свои APK из релиза и завершает работу кодом 0 только после установки;
- обновление на месте с той версии, которую установщик объявляет допустимой. Если допустима только предыдущая, при пропуске версий установщик откажет, и панель покажет его сообщение. Тогда нужно сначала поставить промежуточную версию.

## Чего это не решает

- Откат на старую версию — по-прежнему через SSH.
- Сбой `apk` посреди обновления может оставить панель неработающей, как и сбой при обновлении по SSH. Тогда остаётся SSH и команда быстрого старта.

## Проверка

- Unit-тесты `backend/src/self_update.rs`: строгий разбор версий и порядок как у apk, каталог (только установленная и новее, без черновиков, пре-релизов и дублей), проверка установщика, постоянная программа сервиса, ответ procd (в том числе неизвестный), состояние по рабочему каталогу с правами файлов и отказ при символической ссылке. HTTP-тест: без входа — 401, в preview — `UNSUPPORTED`.
- Тесты фронтенда `frontend/tests/self-update.test.ts`: выбор версий и решение по каждому опросу статуса.
- Стенд, сценарий С9: обновление 0.1.26.4 → лабораторная 0.1.26.4.1 через Tailscale с лабораторного GitHub. Первый прогон С9 нашёл ошибку: файлы результата с правами 0644 отвергались, и удачное обновление выглядело прерванным. Исправлено до публикации.
