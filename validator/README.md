# Экспериментальный изолированный валидатор

`xkeenwrt-validate` — отдельный однопоточный процесс. Он принимает один JSON на stdin до EOF: `{"version":1,"config":"…","assets":[{"path":"providers/example","content_base64":"…"}]}`. Неизвестные поля запрещены. Конфигурация ограничена 1 МиБ UTF-8, декодированные assets — 8 МиБ и 32 файла, относительные пути не содержат пустых компонентов, `.` или `..`. Сырой ввод ограничен 18 МиБ; срок ожидания EOF — пять секунд. Аргументы команд, пути к исполняемым файлам и переменные окружения из запроса не принимаются.

Ответ на stdout — одна строка JSON с фиксированными `status` и `code`; входные данные и вывод ядра не публикуются. Клиент обязан закрыть stdin после запроса и считать `unavailable` отказом. Успешный парсинг конфигурации не является разрешением активации, проверкой соединения или подтверждением работоспособности оборудования.

Исполнение допускается только root в OpenWrt 25.12.6 с ядром 6.12.112 при наличии отдельно установленного root-owned маркера `/etc/xkeenwrt-validator-enabled` (mode 0600, содержимое `xkeenwrt-validation-v1\n`). Установщик пакета этот маркер не создаёт. До отдельного разрешения rollout испытания выполняются только в disposable VM по [ADR 006](../docs/decisions/006-validator-lab-supervisor.md). Должен быть заранее выделен cgroup v2 `/sys/fs/cgroup/xkeenwrt-validation` с memory и pids; core `/usr/libexec/xkeenwrt/mihomo` закреплён SHA-256 отдельно для x86-64 и AArch64. Лабораторные fault hooks дополнительно требуют VM marker и параметр командной строки ядра. Production пакет и рабочие роутеры не являются лабораторией.

Guardian сериализует запросы, владеет job и удаляет только собственные фиксированные пути; monitor запускает полезную нагрузку через gate после проверки cgroup. Дочерний путь использует ограниченный tmpfs, namespaces и seccomp на основе лабораторного supervisor. Положительный статус дополнительно требует независимого подтверждения полноты ресурсов; используется общий crate `profile-policy` для разрешённых профилей и проверенных staged assets; если полнота не установлена, успешный выход core даёт `unavailable/ASSETS_UNVERIFIED`.

Поддержка профилей и ресурсов ограничена правилами общего policy. Проверки в VM не доказывают готовность к работе на физическом устройстве. Лабораторные fault hooks компилируются только с `--features lab-faults` и действуют только после обязательной проверки маркера VM; не используйте такую сборку в пакете.

После аварии самого guardian прежнее задание может сохраняться до отдельного восстановления: `PDEATHSIG` — дополнительная защита, а не доказательство немедленной очистки всех потомков. Runtime обязан запустить фиксированный `xkeenwrt-validate --cleanup` при ненормальном завершении или таймауте и не допускать новое задание до успешного ответа `{"status":"clean","code":"CLEANUP_COMPLETE"}` и exit 0. Этот режим использует тот же guard и общий lock, завершает только собственную cgroup и удаляет только job из собственного пространства имён; ошибка и занятый lock дают `unavailable` и exit 1. Авария runtime одновременно с guardian требует отдельного подтверждённого lifecycle recovery; указанный механизм сам по себе не доказывает такую очистку.

Проверки изоляции, guard и аварийной очистки на полных x86-64 и AArch64 OpenWrt VM, точные хеши исполняемых файлов и границы этих результатов приведены в отчёте лаборатории. Эти результаты не распространяются на другие сборки или физические устройства без отдельной проверки.
